## Goal
Each team has a genre identity with anthem MP3s in the content pack; when a team's MINIGAME_INTRO begins, the display (TV) plays their first anthem — flavor plus an audible "your team is up" summon for scattered players.

## Acceptance Criteria
- [ ] **Schema.** `TeamsContentEntry` (packages/shared/src/content/teams/index.ts) gains optional `genre: string` and `anthems: string[]` (audio filenames), validated **presence-based, exactly like `avatarSrc` in `validatePlayersContentEntry`** (`"genre" in value && !isNonEmptyString(...)`; `anthems` must be an array of non-empty strings when present), accumulating issues rather than early-returning. `Team` (packages/shared/src/team) carries both through `buildTeam` (apps/server/src/contentLoader/loadTeams). `packages/shared` also exports a new `TEAM_AUDIO_ROUTE_PATH = "/team-audio"` constant. No snapshot work: `teams` is already in `DISPLAY_SAFE_ROOM_STATE_KEYS` and passed by reference. **`validateTeamsContentFile` is NOT loosened** — it is shared with `contentWriter`'s save gate (see Plan D4). **Proven in** the existing colocated `packages/shared/src/content/teams/index.test.ts` (7 cases today, extended — not replaced): a team carrying valid `genre`/`anthems` validates clean; `genre: 42`, `anthems: "song.mp3"` (a bare string, not an array) and `anthems: ["", " "]` each produce an issue; and a team with neither field still validates clean. The over-permissive direction is the one that matters — it is silent at runtime AND inherits into the wizard's save gate (D4).
- [ ] **Static route.** `createApp` gains `options: { contentRootDir?: string } = {}` falling through to `resolveContentRootDir()` at call time (the idiom `loadTeams`/`readConfigContent`/`writeContentFiles` already use; `apps/server/src/index.ts` keeps calling `createApp()` unchanged). It mounts `TEAM_AUDIO_ROUTE_PATH` twice — `<root>/local/teams/audio` then `<root>/sample/teams/audio` — as **absolute** `resolve()`d paths, mirroring `loadContentFileWithFallback`'s local-wins fallback. **EXTEND** the existing `apps/server/src/createApp/index.test.ts` — it already carries WN-26's four `WN_DEV_BOARD` gate cases behind a `withApp` helper that calls `createApp()` with no arguments. **Do NOT author it fresh or replace the file**: deleting that coverage would still show green, which is exactly the test-diff regression `rules/testing.md` forbids. Parameterise `withApp` with an optional `contentRootDir` (existing callers unchanged) and add three cases in the shape `routes/health/index.test.ts` already uses (`app.listen(0, "127.0.0.1")` + `fetch`) against a tmpdir content root: seeded file → 200 with `content-type: audio/mpeg`, missing file → 404, and `/health` still 200.
- [ ] **Read-path round-trip.** `apps/server/src/readConfigContent/index.ts:52` (`teams: teams.map((team) => ({ name: team.name }))`) is replaced by a `toTeamsContentEntries` helper written in the shape of `toPlayersContentEntries` directly above it (lines 19–29) — re-adding each optional field by hand. New `apps/server/src/readConfigContent/index.test.ts` (the module's first test) asserts a team with `genre`/`anthems` on disk survives into `ConfigContentSnapshot.teams`, and that a team without them yields exactly `{ name }`. **The write path needs no change** and must not be "fixed" — see Plan D3.
- [ ] **Server-origin URL seam.** `resolveSocketServerUrl` is promoted out of `createRoomSocket` into an exported `apps/client/src/utils/resolveServerOrigin/index.ts`; `createRoomSocket` imports it (behaviour unchanged, existing tests stay green). A pure, exported `resolveAnthemSrc(anthemFileName, serverOrigin)` — **origin injected, never read from `import.meta.env`/`window` inside it** — returns `${serverOrigin}${TEAM_AUDIO_ROUTE_PATH}/${encodeURIComponent(anthemFileName)}`. Colocated test asserts the absolute result for a plain and a spaced filename, and that the return value is never root-relative. The origin is read **only inside the cue effect**, never at render scope, so `renderDisplayMarkup` (react-dom/server, no DOM, no Vite) keeps working.
- [ ] **Unlock overlay.** A new `apps/client/src/components/DisplayBoard/AudioUnlockOverlay/` — three files (`index.tsx` + `copy.ts` + `styles.ts`), mirroring the sibling `GameLockedOverlay/`, as the house lint rules require. It renders **only** when `phase === MINIGAME_INTRO` **and** the active team has anthems **and** audio is not yet unlocked; the unlocked flag persists for the rest of the session so it never renders again after the first tap (per-MINIGAME_INTRO scoping, matching song-guess-spec §8.1). Unlike `GameLockedOverlay` it is `pointer-events-auto`; the pointer handler runs `media.play().then(() => media.pause())` and sets the flag. `DisplayBoard/index.test.tsx` asserts the overlay copy is **absent** at SETUP, INTRO and ROUND_INTRO, absent at MINIGAME_INTRO for a team with no anthems, and **present** at MINIGAME_INTRO for a team with anthems.
- [ ] **The cue.** A `useTeamAnthemCue` hook uses the previous-value-ref phase diff of `useGameStartCountdown` to fire once on entry to MINIGAME_INTRO for `activeRoundTeamId ?? activeTurnTeamId` (the resolution `StageSurface/resolveStageViewModel/index.ts:101` already uses), and pauses + resets when the phase leaves MINIGAME_INTRO. **Setting the `src` and calling `play()` are separate steps:** a single `<audio data-team-anthem>` element carries the resolved `anthems[0]` src whenever a team with anthems is active at MINIGAME_INTRO — *independent of unlock state* — while only `play()` is gated on `audioUnlocked`. (Without that split the e2e in the last-but-one AC would depend on tapping the overlay first, and would go red for the wrong reason.) Every media call is wrapped in the best-effort guard `useTimesUpChime` uses — a rejected `play()`, a blocked autoplay policy, or a 404 audio file never throws and never blocks a phase advance.

  **Proven by exported pure predicates, exactly as the cited prior art does it.** The phase-diff decision must NOT live inside the effect body, because nothing in this repo can observe an effect: client tests run under `tsx --test` with no DOM, `renderDisplayMarkup` is `react-dom/server` (effects never run), and there is no DOM/hook harness anywhere in the tree (no `jsdom`, no `happy-dom`, no `@testing-library`, no `renderHook`). So `useTeamAnthemCue/index.ts` exports two pure predicates alongside the hook — mirroring `useGameStartCountdown/index.ts`, which exports `shouldStartGameStartCountdown` (:7) and `shouldCancelGameStartCountdown` (:19) beside its hook (:31) — and its colocated `index.test.ts` drives them directly, in the shape of `useGameStartCountdown/index.test.ts`. Minimum cases, mirroring that file's three: **fires** on a `previousPhase → MINIGAME_INTRO` entry when the active team has anthems; **does not re-fire** when already at MINIGAME_INTRO (the direct-load / re-render case, matching its "does not start countdown on direct initial ROUND_INTRO load"); **does not fire** at MINIGAME_INTRO for a team with no anthems; and **cancels** when the phase leaves MINIGAME_INTRO, matching its "cancels countdown when phase leaves ROUND_INTRO" case verbatim in shape. This closes the gap that a stuck anthem — still playing over the eating timer and the trivia takeover — would otherwise land fully green.
- [ ] **No-anthem teams unchanged.** A team with no `anthems` renders no overlay, no `<audio>` element and no console error; phases advance exactly as today. Covered by the DisplayBoard render tests above plus the existing display specs staying green.
- [ ] **Content + docs.** `content/sample/teams.json` gains `genre` + `anthems` on **all four** teams, referencing filenames the repo does not ship (no binaries are committed — see Plan D6); hosts drop real files into the gitignored `content/local/teams/audio/`. All four rather than a subset because the e2e content root is seeded from `content/sample` and the spec below asserts on whichever team round 1 happens to make active first — a partial seed would make the spec depend on turn order. The mixed case (a team *without* anthems) is covered at the unit layer instead, where it is deterministic. `docs/minigame-authoring-guide.md` §5.1 is corrected: the cwd-relative `express.static("content/...")` example is wrong for this repo (the server's dev cwd is `apps/server`, and the content root is env-overridable via `WN_CONTENT_ROOT_DIR`) — it must resolve absolute paths from `resolveContentRootDir()` inside `createApp`, not `index.ts`.
- [ ] **The check that goes red on a wrong base URL.** A new e2e spec drives the host to MINIGAME_INTRO (reusing `hostShell`'s `ensureSetupPhase` → `lockTeamsFromSetup` → `startGameFromIntro` → `openTeamBriefingFromRoundIntro`, exactly as `host-display-sync.spec.ts` does), reads `src` off the display's `audio[data-team-anthem]`, and asserts it parses as an **absolute** URL whose origin **differs from the display page's own origin** and whose path starts with `${TEAM_AUDIO_ROUTE_PATH}/`. Port-agnostic and genuinely red-able: a root-relative `src` makes `new URL(src)` throw, and a `window.location.origin`-based src makes the two origins equal. **Then it advances ONE more step** — `hostShell`'s already-exported `startEatingFromBriefing` (tests/e2e/hostShell.ts:85) — and asserts the display's `audio[data-team-anthem]` is `paused`. That is the integration-level half of AC6's stop-on-leave: the predicate test proves the decision, this proves the decision is actually wired to the element.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` and the manifest's `e2e` command all pass (`e2e` is required, not optional — this rewires a spec'd display surface).

## Plan

### Product decisions (grilled 2026-08-07 with the user present — unchanged by the re-plan)
- **Local audio files over Spotify** — offline-safe at a house party, no OAuth/Premium/SDK, and it reuses the asset pattern the song-guess spec already designed. Spotify is parked indefinitely.
- **Assignment lives in `teams.json`** (content pack, `local/` → `sample/` fallback) — no new setup-phase UI. Since WN-19 teams.json is also editable via the admin config wizard's roster editor; MVP scope here is field *preservation*, not wizard UI for picking genres (parked).
- **Cue moment is MINIGAME_INTRO** — the "Team X is up" screen is exactly the summon moment; the anthem plays until the host advances into MINIGAME_PLAY.
- **Display is the speaker** (TV/projector = the room's shared audio). No host-side fallback in the MVP; the host's existing times-up chime is untouched.
- **Best-effort audio** — same stance as `useTimesUpChime`: cue failure must never block the game.

### Re-plan decisions (2026-08-07, autonomous — resolving `.work/verdicts/WN-20.gate1.json`)
Every claim below was verified by reading the source or by running it; the probe results are quoted where they mattered.

**D1 — Audio URL resolution: an explicit server-origin seam. (self-answered — autonomous run)**
Client and server are *always* separate origins: there is no `vite.config.*` anywhere in the repo (re-verified: `find . -name 'vite.config.*' -not -path '*/node_modules/*'` → no results), so there is no dev proxy, and `createApp` serves the client nothing. A root-relative `<audio src="/team-audio/x.mp3">` would resolve against the Vite origin (5173 dev / 5273 gate) and 404. So:
- Promote the module-private `resolveSocketServerUrl` (createRoomSocket/index.ts:15–23) into an exported `apps/client/src/utils/resolveServerOrigin/index.ts` and import it from `createRoomSocket`. One origin resolver, two consumers — a *real* seam by `code-design.md`'s test, not a hypothetical one. (`apps/client/src/utils/<name>/index.ts` is what the `utility-entry-file-name` lint rule requires.)
- The path segment is a **shared constant** `TEAM_AUDIO_ROUTE_PATH` in `packages/shared`, imported by *both* the express mount and `resolveAnthemSrc`. Both apps already depend on `@wingnight/shared`, so client and server cannot drift on the route string and a rename is a typecheck failure rather than a silent 404.
- `resolveAnthemSrc(anthemFileName, serverOrigin)` is **pure with the origin injected** — the same idiom `resolveSocketAuthPayload(pathname, configuredHostControlToken = resolveHostControlToken())` already uses. This is not stylistic: client unit tests run under `tsx --test` with **no DOM and no Vite**, and `AnamorphLab/index.test.tsx:8` and `ContraptionLab/index.test.tsx:8` both exist specifically to pin that a bare `window` / `import.meta.env` read at module *or render* scope throws. A default argument that called the resolver would therefore be untestable. The origin is read only inside the cue effect (effects never run under `react-dom/server`).
- Filenames are `encodeURIComponent`'d — verified against the probe: `GET /team-audio/blaze%20anthem.mp3` → `200 audio/mpeg`.

**D2 — Three checks, and one of them genuinely goes red on a wrong base URL. (self-answered — autonomous run)**
The gate1 rejection's sharpest point was that nothing in the old ACs could fail on a wrong URL. The split:
1. *Client unit* — `resolveAnthemSrc` returns an absolute URL for a plain and a spaced filename, and never a root-relative string. Catches the join logic.
2. *Server unit* — `createApp/index.test.ts` boots on port 0 against a tmpdir content root and GETs the route. Catches "the route serves from the resolved content root". Prior art is exact: `apps/server/src/routes/health/index.test.ts` already does `app.listen(0, "127.0.0.1")` + `once(server, "listening")` + `fetch`.
3. *E2E — the one that catches the wiring.* At MINIGAME_INTRO, read `src` off `audio[data-team-anthem]` and assert `new URL(src).origin !== new URL(displayPage.url()).origin` plus a `${TEAM_AUDIO_ROUTE_PATH}/` path prefix. Root-relative ⇒ `new URL` throws ⇒ red. `window.location.origin`-based ⇒ origins equal ⇒ red. Deliberately **port-agnostic** (no hardcoded 3100/5273), so it survives the WN-5 port pinning.
This also retires the old AC7, which gate1 correctly called near-vacuous: the display renders no interactive elements and no spec has ever clicked it, so "the overlay does not obstruct SETUP" could not fail. Under D7 the overlay cannot render at SETUP *by construction*, and that is asserted in a unit test instead.

**D3 — The field-stripping is on the READ path, not the write path. (self-answered — autonomous run)**
Re-verified against the source. The write path is already clean end to end: `RosterStep/index.tsx` `write: (team, name) => ({ ...team, name })`, `contentDraft/index.ts:56–63` passes the draft file object by reference, `contentWriter/index.ts:119` `JSON.stringify(edit.value, null, 2)` verbatim, and `validateTeamsContentEntry` rejects no extra keys. The loss is at `readConfigContent/index.ts:52` — `teams: teams.map((team) => ({ name: team.name }))`, a fresh one-field literal — so the *wizard never sees* `genre`/`anthems`, and the next save writes them away. The old plan sent the implementer to audit the clean path, which would have produced a trivially-green test at the wrong layer.
Fix: a `toTeamsContentEntries` helper in the shape of `toPlayersContentEntries` (same file, lines 19–29), which re-adds its optional field by hand. `readConfigContent/` currently contains only `index.ts` — this ticket adds its first test file. The AC says out loud that the write path needs no change, so nobody spends the pass "fixing" it.

**D4 — `validateTeamsContentFile` is NOT loosened; "warn and drop" is dropped from scope. (self-answered — autonomous run)**
The same validator is the config writer's save gate (`contentWriter/index.ts:52–54`), and `contentWriter/index.ts:32–35` states the invariant in a comment: read and write validate identically so "nothing can reach disk that the next boot would reject". Loosening it to tolerate malformed `anthems` would silently loosen the wizard's save gate — the one coupling the codebase deliberately maintains. So `genre`/`anthems` are validated presence-based exactly like `avatarSrc`, and an invalid value is a hard failure on *both* read and save, which is the behaviour that already exists. Consequences: the old AC2's "logs a warning and drops" is gone, `logWarn` is **not** added to `apps/server/src/logger` (which today exports only `logInfo`/`logError`), and `loadTeams` keeps its existing fatal-on-invalid guard untouched.

**D5 — Missing audio *files* are not checked at load. (self-answered — autonomous run)**
Filename validity is a schema concern (D4); file *presence* is a runtime concern the display's best-effort guard already covers. So no `existsSync` sweep in `loadTeams` and no fs work in the content loader — a filename pointing at nothing simply makes the `<audio>` element fail to load, silently. This is what lets `content/sample/teams.json` declare anthems the repo does not ship while the e2e still finds a real `src` to assert on.

**D6 — No binaries committed. (self-answered — autonomous run)**
No `.mp3` enters the repo, so the e2e asserts only the *URL*, not a 200. The "route actually serves bytes" half is covered by the server unit test, which writes its own fixture into a tmpdir. Stated explicitly so the implementer does not commit a fixture MP3 to make the e2e greener.

**D7 — Overlay scoping: per-MINIGAME_INTRO, matching the prior art it cites. (self-answered — autonomous run)**
The old AC4 said "until tapped once, persists for the session", implying it renders from page load including SETUP — contradicting `song-guess-spec.md` §8.1, which scopes it to MINIGAME_INTRO and re-renders it on the *next* MINIGAME_INTRO if still locked. Resolved toward the prior art: render iff `phase === MINIGAME_INTRO && activeTeam has anthems && !audioUnlocked`; the `audioUnlocked` flag persists for the session, so in practice it appears once per night and never again. Trade-off, stated: on the very first MINIGAME_INTRO the overlay covers the team-briefing surface until someone taps the TV. That is the cost §8.1 already accepted, and it is the only moment at which a tap can prime the element.

**D8 — A new overlay is a three-file change. (self-answered — autonomous run)**
`tools/eslint-plugin-wingnight` registers `no-hardcoded-component-jsx-text`, `require-styles-import-in-component-entry`, `component-entry-file-name`, `no-inline-style-prop` and `no-hardcoded-hex-colors-in-styles`, so `AudioUnlockOverlay/` is `index.tsx` + `copy.ts` + `styles.ts`, mirroring its sibling `GameLockedOverlay/` exactly. Visual template: `apps/client/public/mockups/locked-overlay/03-heat-locked.html` — the mockup `GameLockedOverlay` was built from (its `styles.ts` still carries the `heat-locked-lock-halo` / `heat-locked-ring` class names). Note `GameLockedOverlay` is `pointer-events-none`; the unlock overlay must be `pointer-events-auto` to receive the tap, and `GameLockedOverlay` must stay as it is.

**D9 — Where the static route mounts, and why not where §5.1 says. (self-answered — autonomous run)**
§5.1's example (`app.use("/minigame-assets/<slug>", express.static("content/..."))` in `apps/server/src/index.ts`) is wrong twice for this repo: the server's dev script is `tsx watch src/index.ts` run with cwd `apps/server`, so a cwd-relative string resolves to `apps/server/content/…`; and the content root is env-overridable (`resolveContentRootDir()` reads `WN_CONTENT_ROOT_DIR` at call time — the e2e stack points it at `.playwright/content`), so a hardcoded path serves the wrong root under the gate. The mount therefore lives in `createApp` — which, unlike `index.ts`, has a test seam — behind a `contentRootDir` option, and resolves absolute paths.
Verified by probe (throwaway express app, since deleted): mounting `local/teams/audio` **first** with the directory entirely absent and `sample/teams/audio` second falls through cleanly — seeded sample file `200 audio/mpeg`, missing file `404`, `/team-audio/../teams.json` and `/team-audio/%2e%2e%2fteams.json` both `404`. So local-wins fallback, correct content-type, and traversal safety all come free from `express.static`'s default `fallthrough: true`; no custom handler is needed.

**D10 — Which team the cue belongs to. (self-answered — autonomous run)**
`activeRoundTeamId ?? activeTurnTeamId`, the resolution the display already uses at `DisplayBoard/StageSurface/resolveStageViewModel/index.ts:101`. Not re-derived.
